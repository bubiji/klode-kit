## 二、新缺口

### P0

#### 缺口 E（K6 / 05b-16）：送出的字节和校验的字节可以来自源文件的两次不同读取

- **攻击**：没有复制，而是先读一次源文件，另一次读取去做校验。
- **能通过全部用例的错误实现**：
  ```
  data = read(src)                       # 第 1 次读：要送出的字节，从未校验
  ok = sha256_file(src) in REG           # 第 2 次读：只用来校验
  crashpoint("send.after_source_read")
  if not ok: exit(60)
  crashpoint("send.after_source_check")
  write(tmp/<sha>.png, data)             # 写副本发生在校验之后，② 满足
  crashpoint("send.after_copy"); crashpoint("send.after_copy_check")  # 纯装饰
  crashpoint("send.before_spawn"); spawn(...)
  ```
- **为什么每条用例都能通过**：
  - 05b-16 的 5 个暂停参数：每个点都在两次读之后，换掉源文件时 `data` 早已是登记过的字节，所以走成功分支，收到的 sha 在登记表内。
  - 05b-16 audit ①：顺序一致。
  - 05b-16 audit ②：第一次写副本发生在 `after_source_check` 之后。
  - 05b-08、05b-07、05b-03：在没有并发的情况下，两次读取得到的字节相同，结果正确。
- **同类变种**：
  - 先把源文件复制到 `tmp/x.part`（或 `work/cache/`），校验通过后再 `os.replace` 成 `tmp/<sha>.png`。② 只记录「对 `tmp/<sha>.png` 的写模式 open」，看不到这次复制。
  - 原子写的正确实现（写 `.part` 再 rename）根本没有这个事件。如果测试写成 `all(...)`，② 空成立，攻击存活；如果测试写成 `index()`，正确实现判红。两种写法 v5 都允许。
- **生产上的后果**：在第 1 次读和第 2 次读之间，源文件被换成未打码的原图再换回来，未登记的字节就会外发。K6 被击穿。
- **要补的断言**：05b-16 audit 运行。L2·S4，contract_replay。
  - **新增 ③**：在 `send.after_source_check` 之前，源文件路径被以读模式打开**恰好 1 次**，并且发生在 `send.after_source_read` 之前。在 `send.after_source_check` 之前，没有任何 argv 中含源路径的 `subprocess.Popen` 事件。
    - 正确设计都满足这一条：「读一次 → 校验 → 从内存写副本」只打开 1 次；「校验 → 按路径复制 → 校验副本」的第二次打开发生在校验之后。
    - 上面的攻击及其变种，在校验之前都至少打开了 2 次。
  - **修改 ②**：观察范围改为以临时目录内任何路径为目标的文件系统变更事件，包括写模式 `open`/`os.open`，以及 `rename`/`replace`/`link`/`symlink` 的目标；创建临时目录本身的 `mkdir` 除外。
    - 要求这类事件**至少出现一次**（非空前提，否则判 FAIL）；
    - 并且全部发生在 `send.after_source_check` 之后。

### P1

#### 缺口 F（K3/K5/K8 / 00s-16）：「所有改变文件系统的事件」不限路径，正确实现也满足不了
- **问题**：v5 把事件集扩成全集，又加上首尾两段，但没有限定路径范围，也没有排除解释器自身的写入。子进程里会出现实现者控制不了的事件：
  - **import 写 pyc**：TDD 过程中源文件不断在改，改完后第一次运行时会出现 `os.open(...__pycache__/*.pyc.<id>, O_WRONLY|O_CREAT)` 加 `os.replace` 两个事件，落在同一段里。
  - **`subprocess` 使用 `DEVNULL`**：会以 `O_RDWR` 打开 `/dev/null`。run_batch 和 build 起子进程时很可能出现。
  - **`tempfile.mkdtemp`**：会在 TMPDIR 下 `mkdir`。
- **后果**：
  - 正确实现会时红时绿：pyc 只在源文件改过后的第一次运行时才写。
  - 实现者为了变绿，最省事的做法是在 hook 里随手过滤，或者在 `crashpoint()` 里塞进无意义的点。这样，缺口 B 的修补就被稀释了。
- **要修改**：00s-16 的 fixture 和断言措辞。L2·S4。
  - 「持久写」定义为：目标路径位于数据项目根、`work/`、`builds/` 或 receipts 目录之下的文件系统变更事件。
  - 明确排除 `os.devnull`、`__pycache__/`，以及本进程在 TMPDIR 下创建的私有临时目录。
  - 子进程设置 `PYTHONDONTWRITEBYTECODE=1`。
  - 断言不变：每一段（包括首段和尾段）至多一次持久写。

### P2

#### 缺口 G（K5 / 11a-13）：租约断言绑定在「写模式 open 租约文件」这一个实现方式上
- **问题**：租约如果用「临时名 + rename」、`mkdir` 或 `symlink` 来建立，就没有「写 B 租约文件的 open」这个事件。这和缺口 E 的 ② 是同一种空成立或不可满足：
  - 测试写成空成立时，「先 load、后写租约」的实现，配上放在两者之后的 `mcp.after_resolve`，可以通过。原问题 P2-7 又回来了。
  - 测试写成要求事件存在时，正确的原子租约实现会判红。
- **要修改**：把「写 B 租约文件的 open」改为「第一个以租约目录内与 B 对应的路径为目标的文件系统变更事件，可以是 open-w、os.open、rename/replace 的目标、mkdir 或 symlink」。要求这个事件必须存在，并且早于 `mcp.after_resolve`，也早于第一次打开 `builds/B/` 内的任何文件。

## 三、建议（不击穿不变量）

1. **08c-10 的单向蕴含放宽过头了**：
   - 一行被删掉时，它自己就属于「被触及的段」，所以**所有**带缺 cell 的记录在全链上都只剩单向约束。那种「忽略 None、其余三路一致就 verified」的实现在 08c-10 上不再被杀；目前 07c-04、07c-05、08a-07 在单层上仍能杀掉它，所以不算缺口。
   - 可以再加一条可满足的计数约束，恢复全链覆盖：对每个被触及的同值段，属于 verified(auto) 记录的行数 ≤ 该段在各路中实际出现行数的最小值。
   - 这是我第 3 轮建议 D 措辞上的疏漏。
2. **00s-16 的清单相等是按参数一一对应，还是对四个参数取并集，没有写明**：建议写死对应关系：writeback↔08c-13，publish 全段↔09d-02，receipts↔00b1-11，run_batch↔04b-13。按「本次运行 == 四份清单」直读，是不可满足的。
3. **§0.3 没有规定 `crashpoint()` 必须发出 `sys.audit("klode_kit.crashpoint", name)` 事件，也没有规定这个事件在测试缝未生效时是否仍然发出**：05b-16、11a-13、00s-16 的 audit 运行都依赖它。建议写明：始终发出，与测试缝是否生效无关。
4. **build 中逐文件 chmod，以及在循环里写多个文件**，在 00s-16 下需要放在循环里的 crashpoint。建议注明：循环点在清单里只算一个名字；09d-02 的枚举只会在第一次经过时触发，后续的覆盖交给随机 SIGKILL。
5. **klode 子进程的写入，hook 看不到**：00s-16 对这部分不构成证明。K5 有「只指向已经过 check 的 build」兜底，所以不算缺口，但建议在 00s-16 的说明里写明这个盲区。
