## 二、新缺口

### P0

#### 缺口 A（K6 / WI-05b，第 2 轮缺口 1 没有真正关闭）：暂停点名字是固定的，位置却由实现者自己决定
- **攻击**：仍然是先复制后校验，但把 5 个暂停点都安排在复制之后。
- **能通过全部用例的错误实现**：
  ```
  shutil.copy(src, tmp/der.png)                 # 先复制，副本从此不再校验
  data = read(src); crashpoint("send.after_source_read")
  if sha(data) not in REG: exit(60)
  crashpoint("send.after_source_check")
  crashpoint("send.after_copy"); crashpoint("send.after_copy_check")   # 纯装饰
  crashpoint("send.before_spawn"); spawn(claude, tmp)
  ```
- **为什么每条用例都能通过**：
  - 05b-16 和 05b-08：5 个点都会写出 reached，所以 reached 门槛满足。测试在每个点替换源文件时，副本早已复制好，假 claude 收到的是登记过的 sha，走的是「成功」那一支。
  - 05b-07：只有一种状态、没有替换。源文件被篡改时，读到的字节也是篡改后的，所以 exit 60。
  - 05b-03 同理。
- **生产上的后果**：真正的竞态窗口在 `shutil.copy` 和 `read(src)` 之间，而这个窗口不在任何一个暂停点之后。源文件「先换成未打码的原图，再换回来」，副本里就是未登记的字节，照样外发。K6 被击穿。
- **要补的断言**：在 05b-16 里增加一个不暂停的正常运行，或新增 `test_send_point_order_and_copy_after_check`。L2·S4，contract_replay。
  - **做法**：子进程装 `sys.addaudithook`，记录崩溃点经过的顺序，以及对临时副本的写模式 `open`。
  - **断言**：
    - ① 观察到的崩溃点序列 == §0.3 send 清单的顺序；
    - ② 第一次以写模式打开 `tmp/der.png`，发生在 `send.after_source_check` **之后**。
  - **说明**：不能写成「源文件只打开一次」。「复制后再校验副本」这种正确设计会打开源文件两次。

### P1

#### 缺口 B（K3/K5/K8 / 00s-16，第 2 轮缺口 4 没有真正关闭）：首尾两段不受约束
- **攻击**：第 2 轮的攻击代码原样就能通过：
  ```
  crashpoint("writeback.before_commit")
  write_effective(rec)          # 在最后一个 crashpoint 之后
  append_commit_marker(cid)     # 同上；之后没有 crashpoint，流程结束
  ```
- **为什么能通过**：00s-16 的断言是「任意两个相邻 crashpoint 之间至多一次持久写」。这两次写都在最后一个崩溃点之后，不在「两个相邻点之间」。08c-13 的随机 SIGKILL 落进这几微秒窗口的概率很低。
- **生产上的后果**：effective 写了，提交标记没写。K3 的「全提交或全回滚」被击穿。
- **要修改**：00s-16 的断言。L2·S4。
  - 把流程的起点和终点也当作边界：起点到第一个崩溃点、各相邻崩溃点之间、最后一个崩溃点到终点，**每一段**至多一次持久写。
  - 审计事件补上 `os.mkdir`、`os.rmdir`、`os.link`、`os.truncate`（也可以写成「凡是改变文件系统的 audit 事件」）。否则把提交标记做成 `mkdir`，就能躲过观察。

#### 缺口 C（K5 / 00s-16 与 09d-02 互相矛盾）：正确实现也满足不了集合相等
- **问题**：
  - 09d-02 的枚举清单覆盖 `pipeline --resume` 的 build → check → publish 全段，「包括 chmod 之前、check 之前」。
  - 00s-16 的 publish 参数只跑「publish 的正常流程」，却要求 09d-02 的清单 == 本次观察到的集合。
  - 两边对不上，正确实现也会判红。
- **后果**：实现者为了让 00s-16 变绿，最省事的做法是把 09d-02 的清单裁剪到只剩 publish 段。这样第 1 轮缺口 5 的修补（覆盖 chmod 之前、check 之前的崩溃点）会被悄悄退掉，K5 中「未经 check 的 build 永不被指向」的崩溃覆盖随之消失。
- **要修改**：00s-16 的 publish 参数改为 `pipeline --resume`，跑完整的 build → check → publish（fixture 用 `fx-publish-ab`）。断言不变，同时套用缺口 B 的首尾边界。L2·S4。

#### 缺口 D（K1 / 08c-10）：真值谓词在跨记录的同值连续段上不可满足
- **问题**：这和第 2 轮缺口 6 是同一类问题。
  - 设一页上记录 R1 的末行与 R2 的首行值相同，都是 v，并且云端路删掉了 R2 那一行。
  - 云端只剩一行 v，正确的对齐也只能任选一侧配上。如果配给了 R2，那么 R1 缺 cell，不会被 verified。
  - 真值谓词却认为 R1「四路齐、没有被删行触及」，要求它是 verified。等价关系失败，正确实现约有一半概率判红。
- **前提**：生成器能产生一页多条记录（有 `record_idx`），并且能产生「相邻同值行」，后者 v4 已明确纳入生成域。
- **后果**：实现者只能把跨记录的同值段从生成域里排除，K1 在 dup 形态上的覆盖又会缩回去。
- **要修改**：08c-10 的谓词。L2·S4。
  - 「被删行或拼行触及」改为按**被编辑行所在的整个同值连续段**判定，与 07b-12 一致。
  - 对与这样的同值段相交的记录，只要求单向：verified(auto) ⟹ 该记录每个 cell 的值 == 生成器真值。
  - 其余记录仍然要求双向等价。
  - 这样仍然能挡住第 2 轮的「按页判断」攻击：那个攻击用的是 approx-only 行，不涉及同值段。

## 三、建议（不击穿不变量，或者属于已决定的范围，可在定稿后再打磨）

1. **11a-13 暂停点的位置**：和缺口 A 是同一种做法。实现者可以把 `mcp.after_resolve` 放在 load 和写租约之后，这样 11a-13 就测不到「先 load、后写租约」的窗口。可以用 audit hook 断言：写租约文件的 open 早于 `mcp.after_resolve`，并且早于第一次打开 B 内部的文件。原项是 P2，所以列为建议。
2. **恢复过程中再次崩溃**：08c-13 和 09d-02 都只「崩溃一次，再跑一次」。可以加一种参数化：在恢复路径上的崩溃点再崩溃一次，断言最终结果不变（幂等）。
3. **生成域保底**：08c-10 和 07b-04 依赖 hypothesis 生成「approx-only 行，同页有 exact 行，四路一致」。建议加 `@example` 把这一形态钉住，避免某次运行恰好没生成出来。
4. **F9 残余风险**：用户 shell 里残留 `KLODE_KIT_TEST_SEAMS=1` 时，测试缝会生效。这属于主会话已经决定的范围，不算缺口。可以考虑让 doctor 在 `TEST_SEAMS=1` 但并非 pytest 环境时给出提示。
